# TsurugiDB Sink 性能測定計画

この文書では、`tsurugidb` シンクの **スループット性能** を評価するための測定計画を定義する。
測定環境（ハードウェア構成、OS、TsurugiDB / Vector のバージョンなど）は本計画では **固定** とし、パラメータとしては扱わない。

---

## 1. 測定目的

- **目的**: `tsurugidb` シンクが、どの程度のイベントレートまで安定して書き込み可能かを把握する。
- **主な観点**:
  - イベント発生速度（入力レート）を変化させたときのシンクのスループット
  - Vector の並列数（ワーカー数やパイプライン並列度）の違いによるスループット変化
  - テーブルの **列数（1, 10, 100, 1000 列）** がスループットに与える影響

---

## 2. 測定対象コンポーネント

- Vector の `tsurugidb` シンク
  - 実際の TsurugiDB サーバーに対して INSERT を発行する経路
  - バッチ処理、トランザクション制御（OCC/LTX）、リトライなど、実運用と同等の設定を使用

---

## 3. 測定データおよびスキーマ

### 3.1 ログファイル形式（入力データ）

- 形式: **CSV**
- 各行は以下のカラムで構成する:
  1. 先頭列: タイムスタンプ文字列
     - 例: `"2025-12-18T07:00:00.000000Z"`
  2. 2 列目以降: `DOUBLE` 値の列
- 列数のバリエーション:
  - `1 列` 構成: `timestamp` のみ
  - `10 列` 構成: `timestamp` + `double` × 9
  - `100 列` 構成: `timestamp` + `double` × 99
  - `1000 列` 構成: `timestamp` + `double` × 999

### 3.2 TsurugiDB テーブルスキーマ

CSV の列構成に対応したテーブルを TsurugiDB 上に用意する。

- 共通:
  - 1 列目: `event_timestamp`（TIMESTAMP 型相当、もしくは文字列）
- DOUBLE 列:
  - 例: `value1`, `value2`, ..., `valueN`（DOUBLE 型）

列数ごとに以下のテーブルを用意する（例）:

- `log_events_1`
- `log_events_10`
- `log_events_100`
- `log_events_1000`

---

## 4. 測定パラメータ

### 4.1 固定条件（測定環境）

- ハードウェア: CPU コア数, メモリ容量, ストレージ種別（例: NVMe SSD）など
- ソフトウェア:
  - OS バージョン
  - TsurugiDB バージョン
  - tsubakuro-rust-core バージョン
  - Vector バージョン / コミットハッシュ
- ネットワーク: TsurugiDB サーバーと Vector が同一ホスト上か、別ホストか 等

※ 上記は測定レポート時に具体値を記載し、**本計画では値を変えない前提** とする。

### 4.2 変数項目（測定軸）

1. **イベント発生速度（入力レート）**
   - 単位: イベント/秒
   - CSV リーダーまたはログ生成ツール側で制御
   - 例:
     - 1 万, 5 万, 10 万, 20 万 イベント/秒 など、環境に応じて段階的に増加させる

2. **Vector の並列数**
   - 想定する並列度:
     - ソース側のスレッド数 / ワーカー数
     - シンク側の同時実行数（`in_flight_limit` など）
   - 例:
     - 1, 2, 4, 8 並列 など

3. **列数**
   - 1, 10, 100, 1000 列
   - ログファイルと TsurugiDB テーブルのスキーマを切り替えて測定

---

## 5. 測定シナリオ

### 5.1 ベースライン測定

- 列数: **1 列**
- Vector 並列数: 最小 (例: 1)
- イベント発生速度: 実現可能な低めの値から開始 (例: 1 万イベント/秒)
- 目的:
  - システムが安定動作するベースラインスループットを把握する
  - 設定や実装上の問題がないか確認する

### 5.2 イベント発生速度スケーリング

- 列数: 固定 (例: 10 列)
- Vector 並列数: 固定 (例: 4 並列)
- イベント発生速度を段階的に上げながらスループットとレイテンシを測定
  - 測定点の例: 1 万, 5 万, 10 万, 20 万 イベント/秒
- 観点:
  - TsurugiDB への実際のコミットレート（イベント/秒）
  - バックプレッシャーの発生有無
  - バッチサイズの変化（実効値）

### 5.3 Vector 並列数スケーリング

- 列数: 固定 (例: 10 列)
- イベント発生速度: ある程度高いが安定する値に固定
- Vector の並列数（ワーカー数/`in_flight_limit` 等）を変更
  - 例: 1, 2, 4, 8 並列
- 観点:
  - 並列度とスループットの関係
  - スレッド数に対するスケール効率

### 5.4 列数スケーリング

- イベント発生速度: 固定
- Vector 並列数: 固定
- 列数: 1, 10, 100, 1000 で変更
- 同一条件下でテーブルとログファイルを切り替え、スループットを比較
- 観点:
  - 列数増加に伴う 1 イベントあたり処理コストの増大
  - JSON シリアライズ/SQL生成/送信サイズの増加の影響

---

## 6. 測定方法

### 6.1 Vector 設定

- `sources`:
  - ダミーの CSV ログファイルを読み込むソースを定義
  - ファイル末尾まで読み切るモード、または疑似リアルタイム再生（指定レートで吐き出す）を利用
- `transforms`（必要に応じて）:
  - CSV → JSON 変換
  - カラム名を TsurugiDB のテーブルカラム名に合わせる
- `sinks`:
  - `tsurugidb` シンクを使用
  - `endpoint`, `table`, `transaction_type`, `batch`, `request` などは README の推奨値または実運用に近い設定を使用
  - 並列度変更時は `request.in_flight_limit` 等の値を変更

### 6.2 計測手順（1 パターンあたり）

1. 対象の列数に対応する TsurugiDB テーブルを準備し、既存データを削除または別スキーマを使用。
2. 対象条件（イベントレート、Vector 並列数、列数）に対応する Vector 設定ファイルを用意。
3. TsurugiDB サーバーが正常稼働していることを確認。
4. Vector を起動し、CSV ログファイルの入力を開始。
5. 一定時間（例: 60〜300 秒程度）連続でデータ投入を実施。
6. 測定期間中、以下のメトリクスを収集:
   - Vector の内部メトリクス（シンク単位の処理件数、エラー件数、レイテンシ等）
   - TsurugiDB 側の統計情報（トランザクション数、コミットレートなど、取得可能な範囲）
7. 測定終了後、TsurugiDB 側のレコード数を確認し、期待値と突き合わせて欠損や重複がないか検証。

---

## 7. 評価指標

- **スループット**
  - 単位時間あたりに TsurugiDB にコミットされたイベント数 (events/sec)
  - Vector のシンクメトリクス、または TsurugiDB の統計から算出

- **レイテンシ**
  - イベント発生（CSV 行がソースに取り込まれた時刻）から TsurugiDB へのコミット完了までの時間
  - 可能であればイベント内タイムスタンプと実測タイムスタンプの差分で評価

- **リソース使用率**
  - CPU 使用率（Vector プロセス、TsurugiDB プロセス）
  - メモリ使用量
  - I/O 帯域

- **安定性**
  - エラー率（リトライ発生回数、失敗トランザクション数）
  - バックプレッシャー/スロットリングの発生状況

---

## 8. 結果整理とレポート

- 各測定パターン（イベントレート × Vector 並列数 × 列数）ごとに、以下を整理する:
  - 実測スループット (events/sec)
  - 平均レイテンシ / p95 / p99
  - CPU/メモリ使用率
  - エラー発生状況
- グラフ化の例:
  - イベントレート vs 実効スループット
  - 並列数 vs 実効スループット
  - 列数 vs スループット / レイテンシ
- ボトルネックの傾向を分析し、必要に応じて:
  - バッチ設定
  - トランザクションタイプ（OCC/LTX）
  - リクエスト設定 (`in_flight_limit`, `rate_limit_*`, `retry_*`)
 などのチューニング方針を検討する。
